# 怎样把这批结果用于课程报告

本文件给出组织方法；可直接使用的正文见[发展任务结果分析报告](发展任务_结果分析报告.md)。本轮继续保持8K，不需要为写报告重新采集。

## 一、主线怎么讲

建议以“局部动作为什么没有接到最终目标”为分析主线。先给80%与37%的总体结果和互斥结局，再比较失败与成功的共同事件，最后用案例解释已经量化的模式。具体共性和可直接引用的段落见[失败共性分析](失败共性分析.md)。

正文最值得保留三个判断。第一，63个跨海未成功实例中54个在建城前失去全部移民，且没有在后续记录中恢复；其中53个已尝试转产，全部8个原生失败均属于这个模式。第二，成功局中29/37也出现粮荒，因此更有解释力的是关键单位是否持续可用，不能只把“粮荒”当失败原因。第三，案例支持预期效果与实际反馈脱节，但这项解释没有全量语义发生率，不能与54/63的状态统计混写。

## 二、建议的正文结构

| 部分 | 回答的问题 | 建议材料 |
|---|---|---|
| 实验设置 | 测什么、预算和停止规则是什么 | 两任务各100、8K、high、4步历史、一次纠错、原生期限 |
| 总体结果 | 成功多少、如何结束 | 结局表与图1；保留每任务100的分母 |
| 输出可靠性 | 首轮错误能否恢复、为何有输出终止 | 图2；区分API请求、逻辑决策、场景 |
| 开销 | 成功与失败分别消耗多少 | 图3与按结局分组的资源表 |
| 共同模式 | 哪些过程在多局重复，和成功路径有什么区别 | 共性对照表/图；54/63全部移民损失，53/54转产但未恢复 |
| 机制案例 | 共同模式如何发生，预期与反馈哪里不一致 | 351解释恢复前提，349/329补充评分及动作语义 |
| 成功参照 | 哪些表面现象不是充分失败原因 | 建城93/948、跨海631/424 |
| 讨论 | 有哪些边界、后续如何验证 | 固定8K、单次场景运行、两任务范围、尚无干预结果 |
| 改进思路 | 如何针对共性改变Agent | 关键状态维护、跨回合风险、恢复前提、预期与观察核对；均为待验证方案 |

如果篇幅紧，保留图1、共性对照表、一个失败案例和一个成功参照。输出纠错计数可用一段说明，完整流程图和其余轨迹放补充材料。

## 三、图表各自怎么解读

图1适合开场。先说明每根柱子都是100局，再分别指出成功、原生失败和输出失败；让读者知道37%的跨海成功率包含了协议层面的终止，而不等于63次已经被游戏判负。

图2解释三个分母。2,726是请求数，2,225是逻辑决策数，200才是场景数。427/501表示纠错后恢复动作交互，不表示427局成功。图的出口写“提交环境”，因为执行了动作也可能与任务目标无关，例如329的造林活动。

图3解释资源关联。调用中位数要同时看成功和失败：跨海成功组9次、原生失败组35.5次。这个差异支持报告资源负担，却不是调用次数对胜负的因果效应；较难场景和恢复过程也会拉长轨迹。

共性对照图是分析的重点：先指出成功局也常出现粮荒，再指出全部移民损失在成功组为0/37、原生失败为8/8、输出失败为46/55。接着讲53/54已尝试转产却没有观察到移民恢复，形成“跨回合维护—关键单位损失—恢复未完成”的共同链条。各行可以重叠，图表示事件覆盖，不是原因占比相加。

图4展示349的评分持续不变以及最后的低分建城。重点讲它的预测如何受到反馈检验，以及原生脚本实际上如何评分。不要把研究者事后查到的静态矩阵规则写成Agent原本已经明确知道。

图5展示631的运输与建城证据。粮荒发生过，但幸存者仍完成目标，所以“出现粮荒”本身不足以判失败。该例与失败场景初始单位数不同，适合作为过程参照，不是备用单位策略的受控实验。

问题标签热力图建议放附录，文件为[figS1_observable_labels.png](figures/figS1_observable_labels.png)。它是多标签的可见现象统计，不是互斥的失败原因分解；成功局也可能带有单位损失标签。

## 四、口头汇报可按六页组织

1. **问题与条件**：两个发展任务各100局，统一high+8K，研究完整交互过程。
2. **结果**：图1与80%/37%，说明三种停止结局。
3. **失败共性**：共性对照图，先用成功局也有粮荒排除简单解释，再讲54/63关键单位全部损失且未恢复。
4. **恢复为什么没奏效**：53/54尝试转产，8个原生失败损失后仍有15.5次动作中位数；用351说明生产投入和人口前提不同。
5. **成功参照与其他机制**：631保住幸存移民；349/329显示预期效果和状态变化脱节，区分全量统计与案例解释。
6. **输出路径与边界**：74局连续触顶空输出，跨海46局在此之前已失去全部移民；固定8K、原生未决与后续验证口径。

这是建议的组织方式，不是课程规定的页数或时长。

若需介绍后续方法，可加一页：用“失败证据—具体改法—待测指标”说明状态记忆与反馈核对，保持high+8K和一次纠错，不展示尚未获得的收益。完整设计见[固定8K的Agent改进方案](固定8K的Agent改进方案.md)。耗时可概括为建城中位数1.8分钟、跨海4.9分钟；平均分别3.3和6.9分钟，8局并行不改变这一统计单位。

## 五、整合总报告时保留的口径

总体成功率继续用80/100和37/100。输出失败发生时原生状态仍未决，保持该事实，不把它们删除后作为新的“真实成功率”。

8K是本轮明确的计算预算选择，相关终止是该配置下需要解释的表现。模型的1M上下文容量不替代单次生成限额，也不意味着这轮设置无效。

两任务只支持两个normal发展任务的结论。战斗、外交和其他方法的表现需由各自结果补充；尚未运行的改进、消融或独立测试，以研究计划呈现，不写成已经获得的提升。

人口提示的时序也应保留：5个跨海原生失败收到该提示，但4个首次提示与终局同一步，只有351还有后续决策。可说恢复前提存在障碍，不能写成5局都看见警告后仍不修正。
