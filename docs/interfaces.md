# 模块与日志接口（设计稿）

本文定义模块应交换的信息，不代表已实现的 Python 类。实现时可以使用数据类或字典，字段语义应保持一致。

## TaskSpec：任务定义

| 字段 | 含义 |
| --- | --- |
| task_type | CivRealm 官方任务类型 |
| difficulty | 本轮使用的难度 |
| objective | 给所有比较方法相同的任务说明 |
| visible_information | 玩家可见的信息范围 |
| score_definition | 原生得分含义及方向 |
| success_definition | 原生成功条件与关键前提 |
| relevant_actions | 用于分析动作相关性的任务定义；若用于筛选动作，需作为实验变量说明 |

## StepContext：一步决策输入

| 字段 | 含义 |
| --- | --- |
| run_id / episode_id / step | 本次运行、对局和动作位置 |
| task_type / difficulty / instance_id / game_seed | 环境实例标识 |
| observation / events | 当前玩家可见的观察与事件 |
| legal_actions | 本步动作编号与对应原生命令的有序映射 |
| task_metrics | 原生小游戏反馈，保留其原始语义 |
| history | 方法允许读取的近期行动、关键进展和反馈 |
| remaining_budget | 其余动作、调用或费用预算 |

legal_actions 的编号只在当前这一步有效。Agent 不能将上一状态的编号直接用于下一状态。

## Decision：Agent 返回

- action_id：当前合法动作列表中的编号。
- reason：简短的选择依据。
- expected_effect：可选，期望发生的可观察变化。
- chat：可选，实际要发送给其他玩家的消息。

不要求模型输出内部思维链。执行器不能根据 reason 中的文字自行补做未选择的游戏动作。

## ExecutionResult：执行反馈

- 实际发送的原生命令与聊天消息。
- 命令是否被执行，以及可观察的响应。
- 下一观察、事件与任务指标。
- 任务是否结束、是否成功，或发生哪一种异常/截断。

命令被游戏接受不等于任务成功。外交聊天发送成功也不等于条约已经执行。

## StepRecord：逐步证据

至少保存任务实例标识、步骤、决策所用观察或其完整记录位置、本步合法动作、模型可见输出、实际命令、前后状态、原生反馈、错误和预算消耗。

记录应能回答：Agent 当时看到了什么，选择了什么，执行器发送了什么，环境确认发生了什么。观察压缩和记忆本身也是方法的一部分，需要能追溯版本。

API 用量记录包括实际模型标识（接口提供时）、请求时间、延迟、输入/输出 token、终止原因与费用估算。凭据不进入记录。

## EpisodeResult：逐局汇总

| 类别 | 字段内容 |
| --- | --- |
| 实验 | 运行标识、方法版本、代码版本、配置与提示词版本 |
| 实例 | 任务、难度、ID、游戏种子 |
| 结局 | 原生任务状态、原生成功字段、运行停止原因 |
| 指标 | 最后观察得分、动作数、回合、调用量、费用、延迟 |
| 证据 | 完整轨迹所在位置、代表案例标识 |

运行停止原因与原生任务状态分开保存。输出失败或预算耗尽时，游戏可能仍处于未决状态；未决不能当作成功。分析层补充失败类别，不修改原始事件。
