# 新批次：32 条动作历史与 16K 输出

这一配置扩大近期动作记录和单次生成预算，用于后续统一采集。它尚未得到新批次游戏效果验证，不能预先声称会提高胜率。已完成的 4 条历史＋8K 结果保留原标签、原始记录和报告。

## 固定的输入规则

每次决策仍提供任务目标、当前玩家可见局面、任务指标、环境事件和通知、有序合法动作及资源信息。输入结构沿用共享 `runner`；`language_state` 原有的科技压缩和地图文字表示也不改变。

历史取本局最近 32 次已执行并收到环境反馈的动作，保持时间顺序。少于 32 次时全部保留；每局重新清空。它按动作计数，不按游戏回合计数；`END_TURN` 也占一条。一次决策中的 JSON 纠错没有执行游戏动作，不单独占历史条目。

每条历史沿用已有字段：

- `native_action`：执行的原生命令（结束回合为 null）。
- `reason`：模型当时返回的简短理由。
- `before_metrics` / `after_metrics`：动作前后任务指标。
- `state_changes`：观测到的单位、城市、生命、移动力或装载关系变化。
- `turn`：环境返回的回合号。
- `native_messages`：已有通知采集逻辑取得的动作反馈；是否完整取决于 SDK 环境，不因扩大窗口而保证完整。

历史不重复包含完整旧局面。更早的动作仍保留在原始轨迹里，但不发给模型。本次没有新增长期计划、模型总结、反思或规则动作。当前局面和合法动作不因扩大历史窗口而被删减。

代码不新增输入 token 硬截断，也不在接近预算时静默丢弃字段；实际输入 token 以每次 API 返回的 usage 为准。超过服务商上下文限制仍按现有接口异常流程保留证据。统一的是输入构造规则，不是每步的输入内容或 token 数。

## 生成与版本设置

新配置 `configs/development_history32_output16k.json` 使用：

- `history_length=32`
- `max_tokens=16384`，是生成上限，不要求每次生成满 16K。
- `method=baseline_history32_output16k`
- 独立 `run_id=development-history32-output16k-20261101`

其他模型、high 思考、top_p、提示词、任务定义、实例、环境动作上限、180 秒请求超时及原有纠错/重试规则与旧配置一致。接口供应商或超时等若另有调整，也须记入实际配置并分开标识；本次配置不包含 OpenRouter 接入或服务器部署。

增加生成预算可能减少截断，也可能增加耗时与费用；180 秒超时仍可能在长生成时触发，试运行应检查。32 条历史也不是 32 个完整回合，不保证包含全部早期计划。

## 显式运行

先在已有可用的 CivRealm 环境中设置 Python 路径、游戏服务和 `DEEPSEEK_API_KEY`。下列例子只采集建城任务的前 5 个场景，不会自动启动其他任务或剩余场景：

```bash
python - <<'PY'
from civstudy.runner import collect
collect('development_build_city',
        'configs/development_history32_output16k.json',
        limit=5)
PY
```

采用 Python 参数调用，避免部分官方 SDK 在导入时把命令行 `--config` 缩写误认成自身的 `--config_file`。游戏服务与 SDK 的其他部署差异仍由各任务环境负责验证。

跨海任务可将任务名改为 `development_transport`。战斗和外交负责人在各自配置中同步历史、输出和版本标识，保留各自任务目标及实例清单；不要套用发展任务清单。

原默认 `development.json` 和监督/分析脚本保持不变。上述新调用会保存独立 run_manifest 和逐局原始轨迹；现有默认分析/同步命令仍针对旧配置及旧报告目录，不能用它们宣称新批次已汇总。新批次汇总需显式读取自己的 run_id 并使用独立报告目录。

参数在每个采集进程启动时读取，不在线修改正在运行的局。新旧结果分别统计；扩大历史和生成预算是两项同时变化，不能凭结果差异单独归因于其中一项。
