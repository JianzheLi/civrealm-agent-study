## 2. 先汇总，再读案例

首先确认记录来自统一基础版本，关联任务、实例和 attempt，基础设施重跑不当作新的独立场景。各任务目标 100 个不同实例，未运行和缺失单列，不用缺失值填零。

逐局表保留原生状态和运行停止原因，按场景汇总：

- 原生成功与原生失败。
- SDK 原生终止但小游戏胜负仍未知，单列 native_terminal_unknown。
- 输出/执行失败。
- 2,000 步宽停止线截断与其他中断。
- 基础设施异常与未运行。

端到端任务表现分母包括已执行策略的原生失败、输出/执行失败和资源截断。尚无可用策略结局的基础设施案例单列，不纳入该分母，但要展示覆盖数；未运行不计策略失败。

调用量包含正常决策、纠错、反思及实际重试。费用和 token 缺失保留未知标记。游戏经过回合以最终减初始回合计算，不混用绝对回合与动作数。

## 3. 怎样分析失败案例

优先每任务选取 2 个失败案例与 1 个成功参照，覆盖真实出现的主要问题，不只选最戏剧性的例子。没有某种结局就说明实际情况，不制造案例。

每个案例按以下结构写一页说明：

1. 场景、模型、基础配置、目标和原生规则。
2. 失败前的关键观察、行动前提和任务阶段。
3. 连续关键步骤：模型输出、实际命令、环境反馈、状态变化。
4. 失败发生处：原生失败、协议错误、执行问题或截断，分别说明。
5. 可直接观察的现象与可能原因，引用 episode_id、decision_id 或步骤范围。
6. 关键帧、进展图或回放位置，以及成功参照显示了什么。

候选分析方向包括目标偏离、关键动作遗漏、无进展重复、反馈未被利用、阶段顺序或多单位配合问题。它们不是既定发现；合理等待、防守与重复要结合状态判断。

每局可有多个问题标签。以场景计每种问题的发生数，同时保存重复次数等步骤级描述；不能把同一局的多次动作当成多个独立失败样本。全组先共享标签定义和例子，再汇总频率。

## 4. 第一轮需要的五类可视化

| 可视化 | 输入 | 具体画什么 | 注意事项 |
| --- | --- | --- | --- |
| 结局分布堆叠条形图 | task_summary 与逐局停止原因 | 五任务各自的成功、原生失败、输出/执行失败、截断，以及异常/未运行数量 | 结局类别互斥；图中注明目标数和实际策略分母 |
| 问题类型 × 任务热力图 | failure_annotations 与场景数 | 每格显示出现问题的场景数/该任务已执行策略场景数，可同时标百分比 | 问题可多选，不要求各行或列加为 100%；说明分母 |
| 调用、动作和耗时分布图 | episode_results | 按任务绘制箱线图或散点，并用结局区分成功、失败和截断 | 包含全部策略场景；缺失值不填零，不仅画成功局 |
| 案例进展图或事件时间线 | 逐步指标和事件 | 横轴用动作或调用，标出任务相关状态、关键动作与最后结局 | 各任务分别解释分数，不平均不同任务原始得分 |
| 地图关键帧、路径图或短回放 | 玩家可见地图、单位/城市位置与事件 | 初始、关键决策、状态转折与结束画面；标出行动单位、目标、动作和回合 | 标明玩家视角/战争迷雾；观察者画面另标，不能冒充 Agent 输入 |

优先用前面三类图比较全组数据，再用后面两类图解释代表案例。图表由相同的结果表与标签表生成，每张图附模型/配置、样本数、分母和数据来源。

后续若需要比较完成速度，可从完整轨迹后处理 success@10/20/50/100/200 次调用；这些 K 值是分析窗口，不是本轮的运行终止线。

## 5. 为了画图，需要在采集时留下什么

除了 [日志规范](logging_spec.md) 的基本字段，还需保留：

- 各步的 env_step、decision_id、game_turn 和关联 call_id，能对齐动作与调用两个时间轴。
- 原生 mini_score、mini_goal 和任务相关状态，避免只有最终分数而无法重建进展。
- 玩家可见地图、可见性范围、地块位置，以及我方和可见对方单位/城市的位置与状态。
- 移动、装载/登陆、建城、攻击伤亡、城市归属、条款变更、接受和科技转移等事件。
- 模型的动作选择、实际命令及对应前后观察，支持定位“想做什么”和“发生什么”。

批量阶段保存结构化状态，选定案例后绘制地图与事件标注，生成关键帧或短回放。基于状态生成的回放注明“状态回放”；实际游戏录屏注明游戏端与视角。不能把重建画面当成原始录屏。

无法从记录确定的动作结果或状态写明未知，不用全局隐藏状态补全模型当时的观察。选定案例的图片与短回放应能关联原始轨迹，完整视频留在服务器。
