# 轨迹、API 账本与结果记录规范

_五任务 LLM 研究的记录约定；单局轨迹、API 账本、结果和批次汇总已实现，人工分析记录尚待实现。_

## 1. 记录的组织

| 记录 | 粒度 | 作用 |
| --- | --- | --- |
| RunManifest | 一次运行配置与场景清单 | 确定版本、规则、参数和运行顺序 |
| StepRecord | 一次向环境提交动作的前后过程 | 连起模型输入、选择、真实动作和环境变化 |
| ApiCallRecord | 每次实际 API 请求尝试 | 统计决策、纠错、反思、重试及费用 |
| EpisodeResult | 一局/一次尝试的最终汇总 | 保存原生状态、停止原因、资源消耗和证据位置 |
| AnalysisAnnotation | 人工或脚本候选分析 | 记录现象与证据，不覆盖原始游戏事件 |

每条记录用 run_id、episode_id 和必要的 step/call_id 关联。重跑的尝试有独立 attempt_id，不能覆盖原尝试。完整观察与请求上下文可保存在独立文件并引用，不必在每一层复制相同正文。

## 2. RunManifest：先确定实验是什么

保存 task_type、difficulty、实例 ID、诊断/开发/测试归属、场景抽样种子、实际可控的游戏随机设置、运行顺序、方法版本、代码版本、提示词版本、环境/上游版本、任务规则与成功条件来源。

保存模型请求参数、实际返回模型标识、基础历史和记忆规则、输出协议、纠错和网络重试规则、原生回合期限、2,000 步宽停止线、每局 API 调用不设独立上限，以及单次费用估算的单价来源。全组统一使用开始首轮时最新发布的 DeepSeek；当前参考版本 DeepSeek-V4.1-Flash-1017，API deepseek-flash。分别保存官方参考版本、核对日期、请求别名与实际返回模型标识，避免将它们混成一个字段。

抽样种子与游戏随机设置分别记录；不支持固定的游戏随机性写明未控制，不用一个 seed 字段声称全部确定。凭据与鉴权头不进入 manifest 或日志。

## 3. StepRecord：模型与环境之间的完整证据

| 内容 | 必须字段或信息 |
| --- | --- |
| 定位 | run_id、episode_id、attempt_id、decision_id、env_step（尚未提交动作时可为空）、当前游戏回合 |
| 环境输入 | 玩家可见 observation、events、原生 task_metrics、当前有序 legal_actions |
| 模型实际输入 | 最终发送的任务说明、观察整理、历史/记忆、单局资源信息和请求 messages 或完整文件引用 |
| 模型最终输出 | 原始 content、解析后的 action_id、简短 reason、可选 expected_effect/chat，以及关联 call_id |
| 解析过程 | 解析或非法编号错误、是否请求纠错、纠错输出和最终是否可执行 |
| 真正执行 | actor_type、actor_id、action_key 与参数、聊天目标和正文、提交时间 |
| 环境反馈 | 反馈时间、明确的接受/拒绝/未知响应、下一观察、事件和原生指标 |
| 任务变化 | 与任务有关的城市、单位、地块、条款、科技等前后状态和进展证据 |

模型输出的理由与执行命令分别保存。执行器不能根据 reason 自行补做额外动作。动作编号只在当前 legal_actions 映射下有效；命令未改变状态，不自动等于命令被拒绝。

输出最终失败而没有提交动作时，仍保留决策与 API 记录，并生成对应 EpisodeResult，不能因没有 env step 就丢弃这局。

不要求保存或索取模型内部思维链。保存最终 content、简短理由和接口提供的 token 统计；如某种工具调用协议需要在请求间传递特定字段，另在该方法的实现说明中交代，不将其用作人工因果标签。

## 4. ApiCallRecord：每次调用都计数

| 字段组 | 记录内容 |
| --- | --- |
| 关联 | run_id、episode_id、attempt_id、decision_id、call_id、用途 purpose、请求尝试编号 |
| 用途 | decision、correction、reflection/planning；其他用途明确命名 |
| 请求 | 发起时间、模型与生成参数、请求 messages 的引用 |
| 返回 | 接口返回的模型标识、最终 content 的引用、finish_reason、响应错误或超时 |
| token | prompt_tokens、completion_tokens、缓存命中/未命中数量，reasoning_tokens（如提供） |
| 时间 | 实际请求耗时；是否由重试产生 |
| 费用 | 调用时单价与时段口径、单次估算费用及用量/费用是否未知 |

一次逻辑决策可能对应多个请求，不能只记一次。实际网络重试要单列；如果 SDK 会自动重试，实现时应能观察逐次请求，或关闭自动重试并由统一入口显式处理。

拿不到 usage 的请求标明 usage_unknown，记录请求尝试，不当成零 token 或零费用。reasoning_tokens 若是 completion_tokens 的子项，不再次相加。费用估算保留缺失说明，不等同于供应商精确账单。

普通决策、纠错、反思和实际重试都进入 api_calls_total。按用途分组的请求数应能加回总数。每位成员采用同一字段，按请求与场景汇总调用、token、耗时和单局费用。

## 5. EpisodeResult：一局结束后汇总

| 类别 | 记录内容 |
| --- | --- |
| 实例和版本 | 方法、任务、难度、ID、随机设置、run/episode/attempt 标识、代码/提示词/配置版本 |
| 原生结局 | native_game_status、native_player_status、原生成功字段、mini_score、mini_goal |
| 运行结局 | success（是否被环境确认成功）、stop_reason、是否资源截断、基础设施异常 |
| 游戏进度 | initial_turn、final_turn、game_turns_elapsed、env_steps、结束回合动作数、聊天消息数 |
| 模型资源 | api_calls_total 与用途分组、输入/输出/缓存/思考 token（可用时） |
| 时间与费用 | 总耗时、API 耗时统计、单局费用估算、未知用量标记 |
| 证据 | 初始与最终状态、完整轨迹路径、调用账本位置、案例录像或截图位置（如有） |

stop_reason 至少区分 native_success、native_failure、output_failure、execution_failure、step_limit、interrupted、infrastructure_error。原生失败由游戏确认；步数停止线和外部中断可能发生在原生仍未决时，不能改写原生状态。

发生基础设施故障时保留 attempt，再按既定规则从同一存档重跑。每个场景、每个方法只贡献一次预定策略试验；原生失败、输出失败或资源截断不以提高成功率为由重跑。尚无可用策略结局的基础设施案例单列数量，不纳入任务表现分母，但已发生的调用与耗时仍保留；批次未开始的场景列在未运行清单，不算策略失败。

## 6. 计数与统计口径

| 名称 | 定义 |
| --- | --- |
| env_steps | 向环境提交游戏动作的次数，即 env.step 调用数；包括结束回合和未生效提交。执行成功数另记 |
| game_turns_elapsed | 最终原生回合减初始回合，同时保存二者；一次回合可有很多动作 |
| api_calls_total | 所有实际模型请求尝试，包含决策、纠错、反思及网络重试；没有每局独立上限 |
| success | 原生状态确认完成任务；文字承诺、高分或命令提交不替代确认 |
| 端到端成功率 | 成功数 / 已执行策略的场景数；原生失败、输出失败和资源截断均在分母内，基础设施异常与未运行单列 |
| success@K | 对同一组场景，累计 API 请求不超过 K 时已确认成功的比例；所有用途的调用均计数 |

提交环境动作的计数与执行是否成功分开；聊天不充当环境动作，单独计条数。无进展事件用于分析，不直接触发自动规则接管或短截断。

按任务报告 planned、started、native_finished、成功/失败、输出/执行失败、资源截断、基础设施异常和未运行数量，给出用于成功率的实际分母。最终测试的配对完整性也要报告，不能把一方尚未运行的场景当作另一方胜出。

开销报告全部场景的分布，再按成功、失败与截断分组；可以补充两方法均成功的配对开销。不能只看各自成功样本的平均调用次数而忽略难度和失败差异。

success@K 从宽松运行的轨迹后处理，建议报告 K=10、20、50、100、200。若案例在 K 前因宽停止线或外部中断被截断，记清未观察部分，不将未知后续当成原生失败。K 超出完整观察范围时不能声称知道无限制运行的成功率。

人工标签可多选，每个标签按场景计数，不能把同一局内每次重复当作独立失败案例。报告分母是全部策略场景还是其中失败场景，并给出证据步骤和标签定义版本。

## 7. 任务特定证据

- 建城：候选位置的玩家可见信息、最终位置、城市创建、任务分数与目标。
- 跨海建城：移民和船的位置、装载关系、运输、登陆、城市创建及阶段顺序。
- 古代陆战：可见单位、生命/移动状态、攻击结果、双方损失及原生胜负。
- 守城：我方城市归属、存活单位、威胁、回合推进和原生期限后的判定。
- 科技交易：发送消息、我方收到的回复、条约条款与变更、双方接受状态、科技实际转移。无法观察的对方收件状态不推断为已接收。

这些是保存观察和事件的要求，不要求执行器用全局隐藏状态补全模型输入。

## 8. 可视化所需状态

为第一轮图表额外保留能对齐 env_step、game_turn 和 call_id 的任务指标、事件，以及玩家可见地图、可见性范围、地块和单位/城市位置。运输保存装载与登陆，战斗保存伤亡与归属，外交保存条款、接受和科技转移。

这些字段用于生成案例进展图、地图关键帧或短回放。状态重建的画面注明状态回放，实际游戏录屏标明视角，不能把二者混称。每张图和每个案例关联模型/配置、样本数与原始轨迹，详细图表要求见 [first_round_analysis.md](first_round_analysis.md)。

## 9. 存储与协作

完整 manifest、逐步轨迹、messages 和调用账本留在本机或服务器的 `run_root`。可恢复批次额外保存 batch manifest、逐 attempt JSONL、精简 CSV 和状态文件；配置和输出位置均由实际运行记录。

Git 保存代码、规则说明、配置、提示词、实例清单、精简 EpisodeResult 表、标签说明与图表。原始观察、完整存档、缓存、模型、视频和凭据不提交。组员用运行标识、路径和证据步骤关联材料，不必复制整套原始数据到本地。

模块接口见 [interfaces.md](interfaces.md)，实验语义见 [experiment_protocol.md](experiment_protocol.md)，范围与参数见 [llm_study_design.md](llm_study_design.md)。
